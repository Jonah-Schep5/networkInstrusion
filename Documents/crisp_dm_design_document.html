CyberGuard Analytics - Network Intrusion Detection System

CRISP-DM Design Document

Author

CyberGuard Analytics Data Science Team

Published

November 30, 2025

Executive Summary

This document outlines the comprehensive design for CyberGuard Analytics’ specialized network intrusion detection system. The project focuses on developing four specialized anomaly detection models targeting Advanced Persistent Threats (APT), Insider Threat Detection (ITD), Phishing, and Zero-day exploits. The system leverages XGBoost machine learning models deployed on AWS infrastructure to provide real-time threat detection capabilities.

Project Objectives: - Reduce Mean Time to Detect (MTTD) by 50% per attack type - Maintain False Positive Rate below 2% - Achieve 18-22% ROI within 3 years - Integrate seamlessly with existing SIEM/SOAR platforms

Data Architecture and Pipeline Design

Overview

The data architecture is built on AWS cloud infrastructure with PostgreSQL as the primary data store. The system processes network flow data from multiple enterprise clients in real-time and batch modes.

Data Sources

Primary Data Source: NETWORK_TRAFFIC_HISTORY Database

Location: AWS RDS PostgreSQL instance
Schema: network_traffic_history table containing:

  • Flow Records: Timestamp, source/destination IPs, ports, protocols, packet/byte counts, TCP flags, service types
  • Client Metadata: Network configurations and security policies
  • Historical Attack Labels: Confirmed cyberattacks with timestamps, attack types, affected systems

Data Volume: ~5 million records per dataset, with continuous ingestion

Data Schema

Key columns include: - timestamp - Flow timestamp - source_ip, dest_ip - Network addresses - source_port, dest_port - Port numbers - protocol - Network protocol (TCP, UDP, ICMP) - duration, packets, bytes - Flow metrics - bytes_per_packet, packets_per_second - Derived metrics - tcp_flags - TCP flag combinations - service - Detected service type - attack_state - Attack classification label - severity_score - Threat severity rating - Temporal features: is_weekend, hour_of_day, day_of_week - Behavioral features: bytes_ratio, packet_size_variance, connection_frequency, unique_ports_per_source

Data Pipeline Architecture

Ingestion Layer

Real-time Stream Processing: - AWS Kinesis Data Streams: Ingests network flow data from client environments - Kinesis Data Firehose: Buffers and batches data for efficient database writes - Lambda Functions: Pre-process data, validate schemas, apply initial transformations

Batch Processing: - Scheduled ETL jobs extract historical data from client SIEM systems - Data validation and quality checks before database insertion - Incremental updates to minimize processing overhead

Processing Layer

ETL Pipeline (Jupyter Notebooks): - data_preparation.ipynb - Creates attack-specific datasets - etl.ipynb - Orchestrates data transformation workflows - data_understanding.ipynb - Exploratory data analysis

Data Transformation Steps: 1. Extract raw network flow data from PostgreSQL 2. Filter and segment by attack type (APT, ITD, Phishing, Zero-day) 3. Feature engineering and encoding 4. Data quality validation 5. Write processed datasets back to database

Storage Architecture

PostgreSQL Database Structure: - Raw data: network_traffic_history (source of truth) - Processed datasets: network_traffic_history_apt, network_traffic_history_itd, network_traffic_history_phishing, network_traffic_history_zeroday - Model metadata: Model versions, performance metrics, training parameters - Feature stores: Pre-computed features for model inference

AWS S3: - Model artifacts (.pkl files) - Training datasets (backup and versioning) - Log files and audit trails

Integration Points

Client Systems: - SIEM platforms (Splunk, QRadar) - Data ingestion via APIs - IDS/Firewalls - Network flow export - SOAR platforms - Alert integration

Internal Systems: - AWS SageMaker - Model training and deployment - CloudWatch - Monitoring and logging - Client Portal - Dashboard and reporting

Data Flow Diagram

Client Networks → Kinesis Streams → Lambda (Preprocessing) → PostgreSQL
                                                              ↓
PostgreSQL → ETL Pipeline → Feature Engineering → Model Training
                                                              ↓
Model Inference ← Feature Store ← Real-time Features ← Kinesis
                                                              ↓
Alerts → SIEM/SOAR → SOC Teams

Model Architecture Specification

Overview

Four specialized XGBoost classification models, each optimized for a specific attack type. All models follow a consistent architecture with attack-specific feature engineering.

Model Selection Rationale

XGBoost Selection: - Handles mixed data types (categorical, numerical, temporal) - Robust to missing values and outliers - Provides feature importance for explainability - Efficient training and inference - Proven performance in cybersecurity applications

Model Architecture

1. APT (Advanced Persistent Threat) Detection Model

Model Type: Binary Classification (XGBoost)
Target Variable: is_apt (boolean)
Training Data: network_traffic_history_apt

Key Features: - Long-term behavioral patterns (connection frequency over weeks) - Multi-vector coordination indicators - Gradual pattern evolution metrics - Temporal features (hour, day, weekend patterns) - Protocol and service combinations

Model Parameters (Typical): - Objective: binary:logistic - Evaluation metric: auc - Tree method: hist (for efficiency) - Learning rate: 0.01-0.1 (tuned) - Max depth: 6-10 (tuned) - Subsampling: 0.8-0.9

2. Insider Threat Detection (ITD) Model

Model Type: Binary Classification (XGBoost)
Target Variable: is_insider_threat (boolean)
Training Data: network_traffic_history_itd

Key Features: - Off-hours access patterns - Unusual data access volumes - Privilege escalation indicators - User behavior baselines - Internal network communication patterns

Model Parameters: Similar to APT model with emphasis on temporal and behavioral features

3. Phishing Detection Model

Model Type: Binary Classification (XGBoost)
Target Variable: is_phishing (boolean)
Training Data: network_traffic_history_phishing

Key Features: - Domain reputation indicators - HTTP request patterns to suspicious domains - Credential submission patterns - Email-related connection timing - Payload pattern analysis

Model Parameters: Optimized for domain and timing features

4. Zero-day Exploit Detection Model

Model Type: Binary Classification (XGBoost)
Target Variable: is_zeroday (boolean)
Training Data: network_traffic_history_zeroday

Key Features: - Novel traffic patterns - Unexpected service responses - Protocol anomalies - Payload anomalies - Unprecedented behavior indicators

Model Parameters: Focus on anomaly detection features

Feature Engineering Approach

Categorical Encoding

Label Encoding Applied To: - protocol (TCP, UDP, ICMP) - tcp_flags (SYN, ACK, FIN, RST, etc.) - service (HTTP, SMTP, DNS, SSH, etc.) - is_weekend (boolean) - source_ip, dest_ip (IP addresses) - source_port, dest_port (port numbers) - timestamp (temporal encoding)

Derived Features

Temporal Features: - hour_of_day - Hour of day (0-23) - day_of_week - Day of week (0-6) - is_weekend - Weekend indicator

Statistical Features: - bytes_ratio - Ratio of bytes in/out - packet_size_variance - Variance in packet sizes - bytes_per_packet - Average bytes per packet - packets_per_second - Connection rate

Behavioral Features: - connection_frequency - Frequency of connections from source - unique_ports_per_source - Port diversity indicator

Feature Selection

  • Remove highly correlated features
  • Drop non-informative columns (e.g., attack_state in training)
  • Retain features with high importance scores from XGBoost

Model Training Process

Data Preparation

  1. Data Extraction: Query PostgreSQL for attack-specific datasets
  2. Feature/Target Separation: Split into X (features) and y (target)
  3. Categorical Encoding: Apply LabelEncoder to categorical variables
  4. Handling Imbalance: SMOTE oversampling for minority class (if needed)
  5. Train/Test Split: Stratified split (80/20) maintaining class distribution

Training Methodology

Cross-Validation: - Stratified K-Fold (5 folds) for robust evaluation - Prevents overfitting and provides performance estimates

Hyperparameter Tuning: - Grid search or Bayesian optimization - Focus on: learning_rate, max_depth, n_estimators, subsample, colsample_bytree

Model Evaluation Metrics: - Accuracy, Precision, Recall, F1-Score - ROC-AUC Score - Matthews Correlation Coefficient (MCC) - Cohen’s Kappa - Confusion Matrix

Model Persistence

Storage Format: Pickle (.pkl files) - apt_xgboost_model.pkl - itd_xgboost_model.pkl - phishing_xgboost_model.pkl - zeroday_xgboost_model.pkl

Version Control: - Model versioning with timestamps - Performance metrics stored with each version - Metadata: training date, data snapshot, hyperparameters

Model Inference Architecture

Real-time Scoring: - Lambda functions load models from S3 - Feature extraction from incoming network flows - Prediction generation with confidence scores - Alert generation for high-confidence threats

Batch Scoring: - Scheduled jobs process historical data - Retrospective threat detection - Model performance validation

Data Quality and Validation Framework

Data Quality Dimensions

Completeness

Target: >95% data completeness
Current State: 5-10% missing entries
Validation Rules: - Check for NULL values in critical fields (timestamp, IPs, ports) - Monitor missing data rates by client and time period - Alert when missing data exceeds 10% threshold

Remediation: - Imputation strategies for missing values - Statistical imputation (mean, median, mode) - Domain-specific imputation rules - Flag imputed values for model transparency

Accuracy

Validation Checks: - IP address format validation - Port number range validation (0-65535) - Protocol value validation (TCP, UDP, ICMP) - Timestamp consistency checks - Byte/packet count logical consistency

Data Quality Metrics: - Percentage of records passing validation - Error rate by validation rule - Client-specific accuracy scores

Consistency

Standardization Requirements: - Consistent time zone handling (UTC) - Standardized protocol naming - Uniform service classification - Consistent IP address formatting

Cross-Client Consistency: - Format standardization across client data - Unit of measurement consistency - Naming convention alignment

Timeliness

Real-time Processing: - Data ingestion latency < 5 seconds - Model inference latency < 100ms - End-to-end alert generation < 10 seconds

Batch Processing: - Daily batch jobs complete within 2 hours - Historical data processing SLA: 24 hours
